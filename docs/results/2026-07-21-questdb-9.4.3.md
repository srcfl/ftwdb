# QuestDB 9.4.3 adapter check: macOS ARM64, 2026-07-21

This is one developer integration check, not an engine ranking. It ran from
FTWDB base commit `98c2ad57dca8f35509295a0cb1100dbd07e085b8` on an Apple M5
host with 32 GiB RAM, APFS, Docker 29.4.0, and a Linux ARM64 Docker VM. Compose
gave QuestDB four CPUs and 4 GiB RAM.

The run used the pinned image
`questdb/questdb:9.4.3@sha256:3fd139f9f16015afc1b064fe4591b271be26cdec10315415e5511e9d80a5919e`
and a fresh named volume. The standard seven-day bundle used one site,
60-second cadence, seed 42, dataset CRC32 `ce8008c0`, and 65,958 points.

| Check | Result |
|---|---:|
| Rows query-visible | 65,958 |
| `points.csv` CRC32 | `3716f745` |
| ILP/HTTP ingest | 0.489 s / 134,864 points/s |
| Site-0 grid points in `[first,last)` | 10,040 |
| Five-minute buckets | 2,016 |
| QuestDB query | 0.0315 s |
| Result CRC32 | `cc32df51` |

The adapter compared count, sum, minimum, and maximum for every bucket. A
second real run used start time `1767225601234567`, which does not fall on a
five-minute or whole-second boundary. QuestDB 9.4.3 returned all 288 buckets at
the exact `start + n * 5m` times under `ALIGN TO FIRST OBSERVATION`; its result
CRC32 was `82607103`. The range excluded the generator's final closing point.

A second adapter call against that same volume stopped before ingest with:

```text
questdb adapter: QuestDB volume is not fresh; existing tables: ftwdb_points
```

The checked unit test also changes one returned bucket sum and confirms that
result verification fails. Parser tests reject a changed CSV header, unknown
summary keys, a bad point count, malformed CRC32, non-finite values, and text in
numeric fields. They also require byte-identical bundle input through import
and reject any table on a volume before the adapter writes. ILP tests cover
symbol and string escaping.

The adapter stores every point and maps portable `change_time` to `event_time`,
with `valid_time` as the designated timestamp. It verifies only site-0 grid
actuals. It does not import catalog or plan records and does not verify DST
calendar totals. These are adapter gaps, not claims about QuestDB's native
features. QuestDB WAL and an ILP/HTTP acknowledgement do not prove the same
durable point as an FTWDB sync.
