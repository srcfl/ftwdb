# Bootstrap benchmark: macOS ARM64, 2026-07-21

This is a developer bootstrap measurement, not a decision-grade comparison.
Criterion ran in `--quick` mode on an Apple ARM64 host with 16 GiB RAM, APFS,
Rust 1.97.1, and no controlled cache drop. The purpose was to validate the
harness and expose the first bottlenecks.

## Append 1,000 points as one transaction

| Engine/mode | Median-ish estimate | Throughput estimate |
|---|---:|---:|
| FTWDB manual sync | 0.555 ms | 1.80 M points/s |
| SQLite WAL, `synchronous=OFF` | 0.647 ms | 1.55 M points/s |
| FTWDB sync each batch | 5.61 ms | 178 k points/s |
| SQLite WAL, `synchronous=FULL` | 0.824 ms | 1.21 M points/s |

The setup phase creates the database and schema outside the timed section. Both
engines write one 1,000-row batch/transaction. This does **not** yet prove equal
physical durability on this hardware; the power-cut suite must validate the
acknowledged durable watermark for each configuration.

The result immediately identifies FTWDB's per-batch sync path as a bottleneck.
Likely work items are group commit, fewer encoded bytes, vectored writes, and
measuring which sync primitive/filesystem barriers are actually issued. The
unsafe/manual mode is not a substitute for durability.

## FTWDB query primitives over 100,000 one-second points

| Operation | Estimate |
|---|---:|
| Latest-revision raw range | 7.90 ms |
| Build 5-minute rollups from raw points | 9.59 ms |
| Read the already materialized 5-minute full range (334 buckets) | 2.67 µs |

The ~3,000x gap between rebuilding and reading materialized buckets is why the
automatic rollup pyramid is a core storage feature. The materialized state in
this original measurement was in memory. M3 now persists and verifies the same
closed state and caches verified rollup segments; its dedicated reproducible
benchmark is `cargo bench --bench rollup -- --quick`.

## Reproduce

```sh
cargo bench --bench compare_sqlite -- --quick
cargo bench --bench storage -- --quick
```

Raw Criterion artifacts are generated under `target/criterion/` and are not
committed. Future benchmark releases will retain machine-readable result JSON,
container digests, input checksums, and physical write counters.

## Immutable segment bootstrap

The M2 synthetic power waveform contains 100,000 one-second points. Its logical
v1 point representation is 7.2 MB; the immutable indexed segment is 696,301
bytes, a 10.34x logical/storage ratio.

| Operation | Estimate |
|---|---:|
| Sort, encode, LZ4-adapt, publish and sync segment | 20.2 ms / 4.95 M points/s |
| Read, verify and decode the full segment | 2.83 ms / 35.4 M points/s |

Reproduce with `cargo bench --bench segment -- --quick`. This is still a quick
developer run, not an SD-card or cold-cache result.

## Persistent rollup bootstrap

The M3 workload contains 30 days of one-minute power data (43,201 points). The
benchmark verifies the persisted 5-minute bucket vector is exactly equal to a
fresh raw materialization before timing either path.

| Operation | Estimate |
|---|---:|
| Cached persistent 5-minute query, 8,640 buckets | 87.6 µs |
| Rebuild the same 5-minute states from raw points | 5.52 ms |
| Cached persistent local-calendar day query, 30 buckets | 2.59 µs |

The persisted 5-minute path is about 63x faster in this warm-cache developer
run. This rerun uses the SD-friendlier layout of one stable file per completed
day instead of one whole-history file, so the query covers 30 descriptors. The
day result likewise covers 30 independent DST-capable descriptors. This
30-day epoch window itself is not the dedicated DST correctness test. Reproduce
with `cargo bench --bench rollup -- --quick`.

## Mixed energy workload versus SQLite

The first M4 native comparison uses one site-day at five-minute telemetry
cadence plus hourly prices, forecast revisions, optimization provenance, plan
metadata, and scheduled setpoints. Both engines are deliberately in unsafe
maximum-throughput mode for this chart: FTWDB manual sync and SQLite WAL with
`synchronous=OFF`. Durable modes remain a separate comparison.

| Operation | Estimate |
|---|---:|
| FTWDB mixed ingest, manual sync | 477 k points/s |
| SQLite mixed ingest, WAL/OFF | 511 k points/s |
| FTWDB cached persistent 5-minute query | 2.55 µs |
| SQLite indexed `GROUP BY` 5-minute query | 98.4 µs |

SQLite was about 7% faster on unsafe ingest; FTWDB was about 39x faster on the
precomputed aggregate query. The query benchmark runs only after exact equality
of bucket start/count/sum/min/max. Reproduce with
`cargo bench --bench energy_compare -- --quick`.

## VictoriaMetrics result-verified telemetry subset

The pinned VictoriaMetrics 1.148.0 image was run on a fresh named volume using
the 7-day, 60-second, seed-42 bundle (`dataset_crc32=ce8008c0`). FTWDB ingested
the complete 65,958-point workload; the VM adapter ingested the 60,414 points
whose `run_id=0`, then verified all 2,016 5-minute count/sum/min/max buckets.

| Measurement | Result |
|---|---:|
| FTWDB full workload ingest, manual sync | 6.72 M points/s |
| FTWDB build all configured rollup tiers | 2.14 s / 168 files |
| FTWDB 5-minute query, cold / warm | 1.44 ms / 0.155 ms |
| VictoriaMetrics telemetry import over HTTP | 1.45 M points/s |
| VictoriaMetrics four MetricsQL aggregate calls | 10.2 ms |

These rows are intentionally **not a direct engine ranking**. FTWDB uses an
embedded call while VictoriaMetrics uses HTTP; the record scopes differ; the
VM query is four calls; and `server_default` durability has not been proven
equivalent to FTWDB manual mode. The adapter result is useful evidence that
the generated telemetry and VM aggregate answers agree, and a foundation for a
later controlled server chart. The VM result checksum was `5e645f22`; its
telemetry-only checksum is not comparable with FTWDB's full aggregate-state
checksum `6b9023b3`.
