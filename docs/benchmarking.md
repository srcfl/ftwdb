# Benchmark protocol

## Principle

No published number is meaningful without the exact commit, database version,
configuration, durability contract, hardware, filesystem, dataset seed, and
warm/cold state. Results are artifacts generated by scripts; README claims
must point to those artifacts.

## Comparison registry

The initial maintained set is FTWDB, VictoriaMetrics, InfluxDB, QuestDB,
TimescaleDB, ClickHouse, tsink, GreptimeDB, Apache IoTDB, TDengine, SQLite,
DuckDB, RRDtool, and ReductStore. TSBS-supported engines also run the standard
TSBS IoT workload. Very large distributed systems are reported separately from
single-node/embedded peers.

Exact versions captured at project initialization include VictoriaMetrics
1.148.0, InfluxDB 3.10.0, QuestDB 9.4.3, TimescaleDB 2.28.3, ClickHouse
26.6.2.81, GreptimeDB 1.1.3, and IoTDB 2.0.10. Container digests, not mutable
tags, must be recorded by the runner.

## Energy workload families

1. **Home edge:** 50-500 series, 1-10 second cadence, irregular gaps, 5 years
   of retained rollups, 1-4 writers.
2. **Fleet:** 100k-10m series, mixed cadence/cardinality, many assets and
   concurrent producers.
3. **Forecast/plan:** overlapping day-ahead and intraday forecasts, optimization
   plans, corrections, scenarios, and strict as-of reads.
4. **Backfill/O3:** live ingest while old telemetry and corrections arrive.
5. **Power-cut:** random termination/truncation at every frame boundary and
   during rollup/manifest publication.

The deterministic generator must include power gauges, cumulative meters,
interval energy, SoC, price, weather, quality gaps, DST transitions, forecast
revisions, optimization plans, and actual outcomes.

The checked-in `bench/fixtures/ftw-real-v1` data adds a fixed replay from a
running FTW installation. Use it to catch assumptions that fit the generator
but not real cadence, jitter, gaps, or value distributions. Its aliases and
time offsets are part of the fixture identity; do not restore source metadata.

## Query suite

- latest point for one and many series;
- raw range scan;
- 5-minute and 30-minute mean/min/max/integral;
- daily energy total and local-calendar monthly total;
- multi-year chart at bounded output resolution;
- plan versus actual grouped by asset and interval;
- latest forecast, complete revisions, and historical as-of forecast;
- fleet/topology aggregate;
- late correction followed by affected aggregate query.

For each query: cold-cache and warm-cache latency distributions, rows/blocks
read, peak RSS, and result checksum.

## Ingest and storage metrics

- points/s and logical MiB/s;
- p50/p95/p99 commit latency;
- acknowledged and durable watermarks;
- database bytes and bytes/point;
- process CPU, peak RSS, and startup/recovery time;
- host/block-device bytes written, sync calls, and compaction bytes;
- write amplification = physical bytes written / logical payload bytes;
- recovery result after an injected failure.

Runs use equal durability where possible: per-batch durable, 1-second group
commit, and unsafe/max-throughput are separate charts. Engines that cannot
offer a mode are marked unsupported rather than silently compared.

## Execution stages

1. Criterion microbenchmarks for frame encoding, checksums, codecs, aggregate
   merge, append, and index lookup.
2. Native embedded comparison on the same APFS/ext4 volume.
3. Single-node Docker comparison with fixed CPU/RAM and named volumes.
4. Linux ARM64 hardware run on the actual target filesystem and SD cards.
5. Long soak plus physical power-cut rig. Docker-on-macOS numbers are developer
   feedback, not SD-card evidence.

The standalone Rust [SD-card emulator](../bench/sd-card-emulator/README.md)
adds an NBD block-device stage between Docker bandwidth limits and target-card
tests. Run FTWDB on ext4, F2FS, or FAT over that device. Keep emulator results
separate from physical-card results and record the profile, seed, fault point,
acknowledged watermark, filesystem repair result, and emulator statistics.

## Statistical rules

Use a fixed seed and input checksum, at least one warm-up, at least five fresh
database repetitions, and confidence intervals. Retain every raw sample. Verify
result equivalence before ranking performance. Do not combine server/network
latency with embedded-call latency in one chart.
